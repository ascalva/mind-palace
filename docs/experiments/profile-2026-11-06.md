# Where the time goes, before anyone argues for Rust (2026-11-06)

**Question.** Six operations are the candidates for a compiled extension. Before one is written,
where does each spend its wall time, how much of that is Python at all, and what would a rewrite
buy end to end? No Rust is written here. One prototype is, in Python, where the profile said the
algorithm and not the language was the problem (Part 3).

## Method, and what the profiler cannot see

Fixtures are synthetic, in a scratch directory, never the live stores, at the live sizes: vectors
17,328 rows at 768 dimensions in float16 (LanceDB; 38 notes of 8 chunks in the shared plane, the
rest code rows); curated 147,057 atom rows (LanceDB; the live count is 147,417, the 360 missing
are the builder's rounding), reference edges 3,029,562 rows over 1,487 commits (SQLite, the real
DDL and indexes, a skewed degree distribution whose hub has 684 citers at the newest cut),
38 notes with 20 relation edges, 196 causal edges. The embedder is a fake that returns a vector
near the notes' topic, so no model time is in any figure. Wall times are the median of 3 to 7
unprofiled runs on a warm page cache; the split is one cProfile run of the same call. The machine
is the owner's Mac with its daemon live, so every figure carries that noise (a few percent).

**py-spy was not used.** It is not in `uv.lock`, adding it would change the lockfile, and on macOS
it needs root. cProfile alone, with three corrections, because cProfile has blind spots that would
otherwise misreport "Python":

1. It hooks Python frames and calls to builtin functions. It does not see a NumPy ufunc or an
   operator (`a @ b`, `x / y`), a LAPACK call under `np.linalg.inv`, or pyarrow's Cython
   (`to_pylist`). That time lands in the caller's own time. So for a numeric kernel the "Python
   share" is measured by a control: the same call at the smallest size that exercises the same
   code path (the floor), which is the interpreter and dispatch cost with the arrays gone.
2. LanceDB's synchronous API drives its Rust runtime through an event loop, so its time is a wait
   in `kqueue`. A `git` child process is a wait in `poll`. They are told apart by their callers
   and counted as LanceDB and as a subprocess.
3. `lancedb/query.py:to_list` is `to_arrow().to_pylist()`: pyarrow's Cython work, counted as
   compiled. Its output is Python floats, which matters below.

"Compiled" in the tables is NumPy and SciPy, LanceDB and Arrow, and SQLite. "Python at all" is
everything else: this repo's code, the standard library, third-party Python glue, and the
interpreter's builtins (object construction, dict and set operations).

The harness lives in the scratch directory of the run and is not committed; the parameters above
and the numbers below are what it measured.

## 1. A sentence's full pipeline

`ask` is compile, plan, universe, evaluate, rank. Over every sentence below, compile is 0.1 to
0.5 ms, evaluate 0.1 to 1.0 ms and rank at most 0.8 ms. The universe build is over 97% of the wall
time of all of them.

One finding changes how every other figure reads. `_resolve_default_commit` asks `git` for the
checkout's HEAD (two child processes, `git rev-parse` and `git status`) unless a run is active
(`core/reference_view.py`). With the palace stopped that is 25 to 45 ms of every sentence that
opens the citation graph, and the profile's biggest single frame. With a run active, as in the
owner's live instance, git is never asked. Both columns are given.

Cold, a fresh engine opening the 147k-atom curated store and running its first `near … over
curated` takes 1.43 s, 84% of it inside LanceDB; warm it is the 78 ms above. The F sentences are
capped by the support bound (200 nodes per anchor), so their dense solve is small: 0.2 to 1 ms.

What the first column says. The `near` family is LanceDB's, and the largest single frame in it is
not search but conversion: reading the 304 note chunks back as Python lists of floats takes 37 ms,
and the same rows through Arrow into a NumPy view take 1.5 ms (measured, 25x). That is a change in
how the reader asks, in Python, not a new extension. The F family is half SQLite (two statements
per node, 12 µs each) and half Python object construction (`ReferenceEdge` rows built for edges
whose only used field is a ref).

## 2. The killed-walk solve (`free_energy_distances`, under `Evaluator._walks`)

A symmetric k-nearest-neighbour backbone of n nodes (10 neighbours each), β = 1.

| support n | edges | wall | Python share (floor control) | top frames | peak RSS |
|---|---|---|---|---|---|
| 100 | 727 | 0.2 ms | about 25% of 0.2 ms (the floor at n = 16 is 0.05 ms) | `inv`, `free_energy_distances` | 40 MB |
| 1,000 | 7,120 | 18.0 ms | 0.3% | `inv` 10 ms, own array ops 7 ms | 119 MB |
| 10,000 | 71,411 | 7,346 ms | under 0.1% | `inv` 5.5 s, own array ops 1.1 s, `reduce` 0.09 s | 7.7 GB |

It is the dense inverse (LAPACK) and the array arithmetic around it. The cost is cubic in n and
8·n² bytes per temporary, and 10,000 nodes is out of reach of any sentence (a sentence's support
is bounded at 200 per seed). No language change touches it.

## 6. `Spine.restrict` and the N_s partition test

Synthetic spines built through the spine's own `_Builder` (so g1, g2 and the acyclicity check are
the real code): version chains per doc with a few long ones, a ledger chain, a derived chain, chat
session chains, chain-less eval events, and about 0.9 cross-store g2 consumers per event. The
sizes are the four at which the `restrict` memo was measured.

| events | chains | longest chain | g1 + g2 edges | the partition test by closure | peak RSS |
|---|---|---|---|---|---|
| 2,801 | 247 | 560 | 5,073 | 483 ms | 80 MB |
| 5,601 | 461 | 1,120 | 10,121 | 2,091 ms | 130 MB |
| 11,201 | 839 | 2,240 | 20,478 | 8,722 ms | 460 MB |
| 22,401 | 1,785 | 4,480 | 40,737 | 36,484 ms | 1.09 GB |

4.3x, 4.2x, 4.2x per doubling: quadratic, as claimed. It is 100% Python (`_reachable`, a BFS per
kept event, with `deque` and `dict.get`). Its shape is a union of chains with cross-store edges
whose heads have several producers: a DAG, not a forest, so interval labels do not apply (they
would need the non-tree edges propagated, which is the bitset case again). Part 3 uses bitsets.

## Prototype: a reachability index in Python (kept)

`restrict` now holds the closure as one bitset per event over the events in topological order
(n²/64 words, built in O(m·n/64), once per spine) and a restriction is a mask over it whose
adjacency is decoded when read. The closure version stays as `_restrict_by_closure`, the oracle a
Hypothesis test checks the new one against on random spines: the same events, the same closed
adjacency, the same generators, the same `order`, `proper_time` and `report`, and a restriction
restricted. The partition test, the index built afresh each run:

| events | by closure | by the index | speedup | by the index, every closure decoded | speedup | peak RSS, closure then index |
|---|---|---|---|---|---|---|
| 2,801 | 483 ms | 6.4 ms | 75x | 32.9 ms | 15x | 80 then 60 MB |
| 5,601 | 2,091 ms | 14.8 ms | 141x | 123 ms | 17x | 130 then 70 MB |
| 11,201 | 8,722 ms | 33.0 ms | 264x | 544 ms | 16x | 460 then 100 MB |
| 22,401 | 36,484 ms | 82.4 ms | 443x | 1,940 ms | 19x | 1,090 then 180 MB |

It stays: it wins by two orders of magnitude on the test as written and by 15x to 19x even when
every closure is decoded, which is the cost of any consumer that reads all of them (the output is
itself quadratic). The index grows 2.3x a doubling (the ORs are O(m·n/64)) against 4x. The one
caveat: these are synthetic spines of an assumed shape, and at the smallest size the saving is
half a second; the case for it grows with the spine.

Reconciling with PR #68, which freezes the dataclass and memoizes `restrict` in a `_restricted`
dict: the index is a `functools.cached_property` (it writes the instance `__dict__`, so it holds
on a frozen dataclass without `object.__setattr__`), and `_succ` is typed as a `Mapping` so a
restriction can carry a view. The memo composes with it unchanged. With the index the memo matters
less (a restriction is a mask, built in O(k)) but it still saves the decode.

## Verdicts

"Python at all" is the measured share of wall time that is not compiled code; Amdahl bounds any
compiled extension by it. A rewrite that makes the Python free gives at most 1 / (that share
removed).

| candidate | wall (live case) | Python at all | a compiled extension, at best | at least 5x end to end? |
|---|---|---|---|---|
| the sentence pipeline, `near` family | 38 to 78 ms | 10 to 19% | 1.2x | No. 70 to 84% is LanceDB, already Rust. The 37 ms float-list conversion is a reader change in Python through Arrow (an estimated 2.5x to 3x on `near`, from the measured 37 ms to 1.5 ms; not measured end to end), no extension. |
| the sentence pipeline, F family | 6 to 26 ms | about 50% | 2x | No. SQLite is 46 to 49% and cannot shrink. One SQL statement per frontier and tuples in place of `ReferenceEdge` would approach that 2x ceiling, in Python (an estimate, not measured). |
| every sentence, with no run active | 44 to 136 ms | | | Dropping the `git` child process (read `.git/HEAD`, or ask once per process) gives 1.7x to 7x on the F sentences (`reach F` from a note 44 to 5.9 ms). It is not a compiled extension; it is a missing cache. |
| the killed-walk solve | 0.2 ms to 7.3 s | under 1% | none | No. 99% is LAPACK. It is cubic and 8·n² bytes; the sentence bounds keep n in the hundreds. Only an algorithm could help, and the diagonal of the inverse that the distance needs makes a sparse solve no obvious win (not measured, so not claimed). |
| the reference BFS and `edge` | 3 to 12 ms; 15 µs | 45 to 49%; 4 to 20% | 1.9x; 1.0x | No. |
| the ingress interpreter | 0.30 µs a step | 100% | plausibly 20x or more on the evaluator alone (an estimate for a tree walker moved to compiled code; not measured) | Yes on the evaluator, and nowhere it is spent: a 10,000-step script is 3 ms and a real door script is dominated by the stores it reads and writes. |
| the predictions bootstrap | 12 ms | 1 to 2% | none | No. NumPy already. |
| `Spine.restrict` and the partition test | 483 ms to 36.5 s | 100% | an estimated 10x to 30x of the constant, still quadratic (not measured) | Done in Python, 75x to 443x, by the index above. |

**What each would cost.** A Rust crate through PyO3 changes the wheel from one pure-Python
`py3-none-any` file to a wheel per platform and interpreter (arm64 macOS, x86-64 Linux CI), moves
the build from hatchling to maturin or adds a second distribution, and needs a PyO3 release that
supports Python 3.15 (unchecked). It adds a toolchain to the owner's `uv sync`, puts crates outside the import
firewall's reach (`scripts/check_imports.py` and `ops.import_lint` read Python imports, not Cargo
dependencies, so the no-network ban for core would need a second enforcement), needs typed stubs
for the mypy floor, and for the interpreter would recalibrate the gas table (the unit is the
measured step) and re-establish the door laws' correspondence with the Lean model. A vectorized
rewrite in NumPy and SciPy costs a function each and nothing structural.

**The candidate with a case, and why it is not yet one.** The interpreter is the only operation
whose time is entirely Python and whose rewrite would clear 5x on its own work. Nothing measured
spends more than milliseconds there, so today the gain is not end to end. Cheaper first: charging
steps in batches takes the 25% the meter costs.

## Findings for the owner

- The `git` child process is the largest frame in a stopped palace's every sentence over the
  citation graph (25 to 45 ms of 44 to 63 ms).
- The 768-dimension vectors come back from LanceDB as Python lists of floats for the whole mirror
  on every `near`: 37 ms, against 1.5 ms through Arrow. This is the live case's main cost.
- Nothing here argues for Rust. Two of six candidates have a Python-level change worth 2x to
  443x; one is a compiled-code case that has no workload; three are already compiled.
- The fixtures are synthetic. The live spine, the real degree distribution of the reference
  graph, and a real embedder's latency are not measured; re-run on the live shapes before acting
  on a figure that is within 2x of a decision.
